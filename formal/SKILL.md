# Verify DrexPolicy

Activate this worktree's `.venv`, then run from the repository root.

```sh
make formal
```

The command runs offline without an API key and writes its evidence directory to stdout. Exit 1 means a checked property broke or a required mutant survived. The runner updates `formal/evidence.json` and verifies that all formal artifacts are visible to git, except `.tools/` and caches. Read `summary.json` for the verdict, `baseline.json` for replay and input counterexamples, and the corresponding `tlc.log` or worker log for details. A traceback from the runner itself means the check did not finish. Run `make qa` separately with `.venv/bin` on `PATH`. The default pytest run collects tests from `tests/`.

The worktree has TLC 2.19 from TLA+ Tools 1.7.4 in `formal/.tools/tla2tools-1.7.4.jar`. On another checkout, install Java 11 or later and place the [TLA+ Tools 1.7.4 release jar](https://github.com/tlaplus/tlaplus/releases/download/v1.7.4/tla2tools.jar) at that path before the offline run. The runner pins SHA-256 `936a262061c914694dfd669a543be24573c45d5aa0ff20a8b96b23d01e050e88`. The runner uses `OfflineTLC.java` to replace the standalone fingerprint store's unused RMI listener with an unbound socket. TLC checking and state storage use the pinned jar. SANY and TLC can also be run through `tlc-java` when applying `/statechart`. The launcher requires a JDK with Java source-file execution. The run uses the installed development dependencies and blocks Python socket connections and DNS. The model and replay use synthetic data.

## Models and replay

TLC explores the order of bounded events. The Python checks exercise the implementation with generated inputs because there is no direct verifier for the Python/Guardrails/SDK stack here. Hypothesis samples the domains below.

- `Validation.tla` represents one initial validation plus at most one replacement. The modes are `raise`, `fail`, and `pass`. It covers all eight correction actions on a threshold failure and uses `noop` and `fix_reask` for the broader reply matrix, including an unusable answer masked by invalid usage metadata. Routes are sequential `Guard`, default `Guard` with a sync client, `AsyncGuard` with a native async client, and `AsyncGuard` with a sync executor client.
- `RefuseInput` maps to preflight in `main.py:112–157`. `CallDrex` and `CallReplacement` map to the cancellation-flag read and SDK invocation in `main.py:339–350`. They are atomic model actions under the thread commit-point contract described in LIMITS. `CancelExecutorBeforeCall` occurs before that commit point, and its replay gates image preflight, delivers cancellation, waits for `CancelledError`, then releases the worker and checks for zero calls. `ReturnResult` and `ReturnReplacement` combine SDK completion with result handling, which has no native async await. `EnterExecutor` and `EnterReplacementExecutor` mark preflight in a worker. `CancelInFlight` represents caller cancellation after commitment and permits a sync worker to complete in the background.
- `CorrectOriginal` corresponds to `SequentialValidatorService.run_validators` and `AsyncValidatorService.run_validator` calling `perform_correction`. The replacement result is passed to the original correction. A failing or undecided replacement raises from `_check_replacement` and the error path calls it before applying `on_error`, and an exception from replacement validation permits the original correction count to remain zero. `P1Accepted` additionally requires a real passing answer for a passed replacement. `fix_value` is configured for `fix` and `fix_reask`. The duplicate-delivery variant repeats failure consumption at that boundary.
- `Concurrency.tla` uses one shared validator, two guards, two distinct Noul answers (0.1 and 0.9), and every ordering of request entry and response completion. Worker threads can also switch between answer extraction and the next line of `_result`. Native tasks run that code without yielding. The replay gates SDK completion and, for workers, gates the identified source line.
- The runner extracts the full baseline TLC graphs and replays every non-stuttering terminal path. It checks the number of parsed states against TLC's count. Completed terminal self-loops are excluded from replay. The runner checks model mutations by invariant name and code mutations against focused real-code checks. Each killed variant also has an unmutated control that runs the same check.

For both models, read every result with the pstack `/statechart` skill. Use the matching config and view in this directory. The default validation configuration checks all routes. `ValidationChart.cfg` is a diagram slice with `on_error="pass"`, `on_fail="fix_reask"`, and the native/executor routes. The unrestricted model supplies the full verdict. For a model mutant, use its model and config from the evidence directory with the same view. Relate each shortest path to the named code boundaries and compare it with the replay. A model path that lacks a matching concrete execution needs a model review. For a replay failure, inspect the calls, result, corrections, and actual control flow before deciding whether it is a product bug or a harness error. For an intended change, update the model, replay, generated checks, and mutants together. Advance the recorded sync commit and source hash only after the updated verification matches the code.

## LIMITS

- On the thread path, the cancellation-flag read immediately before `system_one` is the request commit point. A cancellation delivered before that read prevents the call. The model treats the read and call as one atomic step under this contract. Once the read has committed the request, cancellation can no longer stop it, including when cancellation arrives between the flag read and SDK entry. The worker has no later decision point that can guarantee an interruption before every possible thread switch. This is a limit of the code, and the check does not establish the stronger guarantee of preventing every SDK entry after cancellation. An already committed sync request may finish while the caller receives `CancelledError`. On the native async path, cancellation must propagate and stop the transport call.
- Generated checks use up to 80 examples per property function and explicit boundary cases. Noul measurements and thresholds include `[0,1]`, and Score comparisons use finite binary64 values across their domain. Unusable measurements include NaN, infinities, nonnumeric fields and out-of-range Noul values. HTTP sampling includes caller statuses 400, 401, 402, 403, 404, 422, 499, availability statuses 408, 429, 500, 529, 599, connection and timeout errors, unreadable JSON, and unusable answers with both valid and invalid usage metadata.
- Answer preservation checks Noul with or without confidence and Score with up to five probability entries and legend labels. Image sequences contain zero to ten entries drawn from base64, data URLs, and workspace references. Data-URL payloads use the same alphabet, padding, and length rule as bare base64, with generated payloads through length 40 and explicit invalid and valid boundaries. Replacement checks cover all three error modes, passing and failing answers, unusable data, availability errors, and caller errors. Caller errors retain their exception instance. The SDK wire request is captured with `httpx.MockTransport`. Metadata includes generated ordinary keys, nested values, and ordered images. Error redaction uses generated body text for 408, 429 and 5xx, with and without a request-ID header. Request IDs include arbitrary Unicode strings through length 145 and ASCII identifiers through length 140. The accepted domain is `[A-Za-z0-9._:-]{1,128}`. The check permits validated request identifiers from either SDK source, including its body fallback.
- The checks cover one installed dependency pair, non-streaming string validation, supplied fake or mock-transport clients, one replacement, and two concurrent calls. They leave live transport, SDK retry timing, client lifecycle, framework version differences, streaming, stopping an already in-flight sync request, and arbitrary real inputs outside the checked scope. P6 counts validator invocations of `system_one`. An SDK retry can make additional HTTP attempts internally.
